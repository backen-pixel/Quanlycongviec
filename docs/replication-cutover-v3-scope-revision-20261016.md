## Explicit finite sequence

The production entry point is `backend/scripts/coordinate-replication-cutover-v3-20261016.js`. It has the same explicit finite action names as V2. There is no implicit action, migration install, deployment, restoration, replay, pruning, broad grant or automatic retry.

1. Independently review the new SQL, coordinator and repair copy; run all synthetic tests and genuine PostgreSQL 17 tests at the final source SHA. The five original source hashes remain pinned. Reinspect current metadata, runtime identity, flags and database capacity after any external change.
2. Establish a quiet window for owner DDL before any live arm/fence/capture. Install the new ledger SQL through the separately reviewed operator path. Build the full revised plan using fresh read-only inventories and the original base descriptor. If any difference exceeds the exact addition, stop without changing scope.
3. Prepare a fresh `cutover_source_review_v3` approval binding run UUID, original hash, revised hash, both SQL hashes, all seven source hashes and explicit allowed actions. Old `cutover_source_review_v1` approvals are rejected. Prepare fresh separate capacity attestations for the complete revised plan on each site; original base-plan capacity approvals are rejected.
4. Run `init` on primary and backup sequentially. This appends each revision ledger row only while the existing control is inactive. It does not create or reset control/run state. Run `register --tables _bulk_hoanthanh_sx_20261016 --site primary` once. Backup needs no registration action. Validate both full scopes.
5. Under the separately reviewed maintenance procedure, explicitly activate/renew both fences by current-epoch CAS with a fresh deadline of at most 15 minutes. Acquire current capacity/source approvals before each action. Init/register/activate recheck those approvals immediately before COMMIT. Deadline expiry keeps the database closed; it does not reopen writes.
6. If both complete fences are active, a complete closing-only capture is supported: capture and freshly verify primary, then backup, using stable per-site capture UUIDs. Two retained-capture slots remain budgeted even when no baseline is needed. Closing locks all revised public tables before establishing its snapshot, checks the current full scope and exact active epoch, remeasures serialized size, and rechecks source/capacity at each plaintext boundary and before COMMIT.
7. Preserve durable receipt/capture metadata, the revised plan, approval and key identifiers before changing a Render instance. Only a separately reviewed exact deployment with the worker disabled, proof the old unsafe process has stopped, successful full capture verification and fresh active epochs can admit the new bounded repair. This file performs none of those provider actions.
8. The separate V3 repair uses context `{run_id,base_manifest_sha256,manifest_sha256,epochs:{primary,backup}}`. It calls `readRepairSite(client,{site,context})` inside an already-open transaction; that validator does not BEGIN, COMMIT or mint a permit. It validates both manifests, all current public registrations/hooks and the active unexpired site epoch under `FOR SHARE`. The authenticated snapshot includes this deterministic context. Renewing an epoch or deadline requires a fresh repair snapshot. Old repair contexts/snapshots are rejected.
9. Release is explicit CAS. It still verifies private/base/revision/source identity, but does not require current public scope, current flags, or unexpired review/capacity. This abort path remains available after the originally observed scope-race failure. The unchanged V2 release path remains separately available with its original reviewed inputs.

Persist action intent and identifiers before dispatch. A failed or missing COMMIT acknowledgment is an unknown outcome and requires fresh inspection; it is never an instruction to retry with new IDs. Each site's revision/capture commits independently; a partial two-site result must be inspected and completed explicitly. Nothing in the new ledger makes two databases atomic.

## Prerequisites and limits

The DML fence does not prevent owner CREATE/ALTER/DROP. Inventory under repeatable read also cannot prove that future DDL will remain quiet. **This candidate therefore requires an explicit quiet owner-DDL window; it does not add or claim a DDL guard.** The previous failure correctly held when another table appeared between measurement and activation. Maintenance UI alone does not prove a database DDL freeze. A separately reviewed guard would need another change.

Readiness remains false. A revised manifest and private ledger alone do not prove complete cutover, old-process termination, capacity, storage parity, recovery of historical lost RAM jobs, old delete intent, replica identity reconciliation, Ads acceptance or a qualified customer. Current LIGHT/storage-disabled REST coverage is the intended capture scope; it does not certify historical storage bytes. Current-state capture preserves rows and committed journals visible in its protected snapshot, including target-only rows and no-PK multiplicity, without applying them anywhere.

The scope suite uses actual isolated PostgreSQL through PGlite; it replaces only the fixed base-hash literal because synthetic OIDs cannot produce the production base SHA. There is no such override in the production entry point. Its exported runner can use the existing guarded loopback PostgreSQL 17 factory. Genuine multi-session coverage is required for the final source SHA, especially old writers versus fence activation, registration/catalog lock races, owner-permit writers versus closing snapshots and unknown COMMIT outcomes. Synthetic fixture checks are not evidence that production was changed.
