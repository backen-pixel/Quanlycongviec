# Finite cutover coordinator candidate — 15 October 2026

`backend/scripts/coordinate-replication-cutover-v2-20261015.js` coordinates the reviewed v1 five-table identity journal, v2 remaining-table digest journals, a durable statement write fence and encrypted per-site captures. This is a separately reviewed operator CLI. It installs no schema, deploys nothing, restores no business rows, creates no role grants, performs no replay/clone/pruning and never releases a fence automatically.

The candidate always returns `cutover_ready:false`. An individual site's successful operation is evidence for that operation, not proof that the other site is protected, an old Render process has stopped, historical RAM jobs were recovered, or a backup is reconciled.

Capacity evidence uses fresh provisioned/used/free disk observations, positive additional WAL/temp/safety/journal reserves and scalar serialized sizing of **every** site's base table. Measurements, UI observation and attestation must remain within 15 minutes. The number of retained reserved capture IDs, including unresolved outcomes, cannot exceed the approved retention budget. Capacity attestation version1 retains its conservative twice-raw JSON escape bound. Explicit version2 additionally requires each table's `encoded_bytes`, measured as `sum(octet_length(to_jsonb(to_jsonb(t)::text)::text))`: the UTF8 size of PostgreSQL's JSON-encoded raw-row string. The candidate tests this against Node's `JSON.stringify(raw)` for controls, quotes/backslashes, Vietnamese/non-Latin1 text and exact numeric JSON. Version2 uses that observed envelope plus 16 bytes per row and reviewed metadata/chunk overhead, preserving storage factor2, at least two retained captures and every positive reserve. Capture remeasures encoded bytes in the same snapshot; unchanged raw sizes cannot conceal increased escaping. This refinement is evidence-based sizing, not permission to reduce reserves or assert real capacity from disk size alone.

The primary's measured maximum raw row is 12,547,819 bytes. The revised candidate supports 16 MiB raw rows, 32 MiB encrypted chunks and a 128 MiB raw FETCH budget capped at 4096 rows. Large rows remain byte-limited to 10 per FETCH; small tables avoid thousands of unnecessary roundtrips. Full UTF8/numeric and 4096-row two-byte-string benchmarks must run against genuine PostgreSQL17.6; PGlite memory includes its database engine and is not a production Node client profile. Large rows are never skipped. Any larger row or expanded JSON chunk still holds before an unsupported transfer.

## Finite operation sequence

Every invocation selects exactly one action and one site. There is no default action and no two-database atomicity claim.

1. `inspect` returns private control/run/registration and capped receipt metadata. `measure` and `validate` are read-only. `validate` verifies exact v1/v2 private/public contracts; it does not prove full registration unless the later full-coverage gate runs.
2. `init` inserts the exact frozen plan/run and an open control epoch. It requires capacity/source review but changes no business rows.
3. `register` accepts at most five exact plan table names. A transaction takes `SHARE ROW EXCLUSIVE` locks on that batch before its first MVCC read, validates catalogs/registrations and atomically adds the exact ALWAYS fence plus the v2 row journal where applicable. The five `v1_external` tables receive only the v2 statement fence; v1 remains their sole row journal. Existing correct registrations are verified and retained.
4. `activate` requires all approved tables registered, exact combined repair support, fresh capacity/source review, expected current epoch, unique new epoch and an explicit deadline no more than 15 minutes ahead. `transition_fence` drains existing writers through its control-row lock. Each site is activated explicitly. A site failure is held for inspection; the CLI never silently undoes the other site's completed activation.
5. Obtain fresh same-state scalar sizing after the fences if necessary. `capture` requires explicit baseline/closing phase, capture UUID, key UUID and a dedicated 32-byte base64 key delivered through silent standard input. No JWT or auth secret is used. Reservation is committed separately in a SERIALIZABLE transaction, including the retention count predicate; artifacts and the immutable committed receipt share a second transaction. A committed receipt with missing chunks is evidence loss, not permission to replace a capture.
6. A closing capture takes `SHARE` locks on **all** approved public base tables before its first MVCC read. These drain even reviewed owner-permit writes and prevent new writes through capture COMMIT. It also holds the exact active, unexpired control epoch `FOR SHARE`. Scalar sizes are rechecked inside that snapshot against the approved per-table bounds before plaintext. All table rows remain raw PostgreSQL JSON strings inside AES-GCM ciphertext, preserving numeric/bigint values and no-PK duplicate multiplicity. All committed v1 and v2 journal events are re-enumerated in every capture, including lower sequence IDs that committed late; no max sequence/transaction/time watermark acknowledges anything. Schema/plan metadata and all expected stream digests are authenticated. Capacity/source expiry is rechecked before every table stream, every journal FETCH and final COMMIT boundary.
7. `verify` runs a new read-only transaction and authenticates the complete committed artifact set and manifest. Both sites' verified closing captures, durable fences, reviewed combined repair and explicit old-process/maintenance evidence remain separate rollout gates owned by the operator.
8. `release` is an explicit audited owner CAS with expected epoch and a unique new epoch. It still verifies private source/run contracts. It intentionally does not depend on fresh capacity, process flags, an intact public catalog or an unexpired review timer; these must not prevent an operator's reviewed recovery/abort. A missing or stale epoch never opens the fence. Deadlines and process death never reopen it.

Any exception after dispatching COMMIT is reported `CUTOVER_LIFECYCLE_COMMIT_OUTCOME_UNKNOWN`, with only site/run/capture/receipt/action identifiers. Use a fresh `inspect`/`verify` and the same identifiers; never infer rollback from a lost response and never mint a replacement capture blindly. The other site may have committed independently.

## Availability and remaining acceptance

Normal reads remain available while the active fence rejects unpermitted writes. An active expired fence stays closed and requires explicit owner recovery. Ending a CLI session releases its transaction locks but not the durable fence. The only bounded parent repair bypass is minted inside the reviewed real repair transaction and tied to owner session, backend PID, full transaction ID, run/epoch, exact table OIDs and INSERT/UPDATE operations. The coordinator does not mint a general permit.

Local lifecycle tests cover finite gates, preservation of original v1 catalog hashes, complete registration, raw numeric/no-PK snapshots, low-sequence deletes, same-snapshot growth, retained reservations, explicit release under expired evidence, COMMIT-response loss and expiry at journal/precommit boundaries. Genuine PostgreSQL17.6 must additionally exercise coordinator-specific concurrent reservations, closing lock ordering versus owner permits and process/connection failures; the earlier nine helper fence tests do not prove the whole coordinator. Complete real capacity attestations, fresh public plans, both-site live verification and old-process evidence are still required before production actions.

This preserves current states and subsequent covered changes. It does not reconstruct already-lost RAM job payloads, prove unknown historical delete intent, copy storage object bytes, repair the 11 shared schema drifts or authorize deleting backup-only rows. Historical identity/tombstone uncertainty remains explicit and unmatched restoration/deletion is held.
