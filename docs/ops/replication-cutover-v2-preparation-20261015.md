# Generic cutover v2 — local preparation only

This candidate adds new files and the separate `vpt_cutover_v2_20261015` namespace. The committed five-table v1 function, schema, runtime and three-row repair contract are unchanged. No production migration, trigger, fence, snapshot, queue action, data restore, deployment or resource/cost change has been performed by this candidate.

The CLI `backend/scripts/prepare-replication-cutover-v2-20261015.js` exposes **read-only inventory/plan only**, optionally writing a new local metadata plan file with `--plan-output`. It has no arm, capture, fence, release, replay, restore or prune command. Low-level exported helpers exist for isolated tests and future reviewed coordination; their presence does not make them production operations. Readiness remains false for capacity, fence coverage, old-process shutdown, combined v1 repair integration and historic RAM recovery.

## Reviewed preparation surface

- `database/20261015051758_replication_cutover_v2_preparation.sql` was created with Supabase CLI 2.120.0 `migration new replication_cutover_v2_preparation` and moved to the repository's migration directory. It creates only private logged tables/functions, with forced owner-only RLS and application ACLs revoked. It attaches no public trigger.
- The complete metadata plan applies the actual light/default/custom skip rules and binds per-site project identity, relation OID, ordered PK types/columns, column/default hashes, constraints, trigger definition/enable mode/function-body hashes, read-only view definition hashes and held exceptions. View dependency closure is recorded in the separate feasibility audit; it is not an explicit field in this plan. Inheritance/partition routing, write rewrite rules, unsupported keys or invalid relations are held.
- Generic row journal primitives hash canonical database PK JSON (including table and ordered key descriptor) and old/new whole-row JSON. Raw text/composite keys, contacts and credentials are not journal payloads. No-PK tables record digest multiplicity and require encrypted row multisets, without an invented unique identity or automatic delete instruction. The five v1 tables are marked `v1_external`; a future coordinator must retain and validate their existing journal separately rather than install the generic row trigger there.
- Lossless export primitives require repeatable-read/serializable transactions, set UTC, premeasure same-snapshot row/byte bounds, use a forward cursor and adaptive byte-based chunks, and preserve database JSON as strings. The reviewed candidate caps raw rows at 16 MiB and serialized encrypted chunks at 32 MiB. Each FETCH uses at most 64 rows and a scalar-sized raw budget of 128 MiB. Actual primary sizing found three tables above the previous 4 MiB row cap (maximum 12,547,819 bytes); none is omitted. Numeric/bigint row values are never parsed into JavaScript numbers. Memory and actual-server tests must pass before these expanded limits are used live.
- Dedicated 32-byte recovery key/version encryption uses a v2 HKDF domain and AES-256-GCM AAD binding project pair, run, capture, site, phase, schema manifest, fence epoch, stream, part, count and key version. No JWT key or relaxed TLS is used. Verification fetches/decrypts one ciphertext chunk at a time, caps artifact metadata at 100,000 parts and computes the set digest incrementally.
- A separate append-only reserved receipt precedes an artifact transaction. Its committed receipt is inserted in **the same transaction as all chunks and their authenticated manifest**. A visible committed receipt with any/all missing artifacts holds; it never permits recapture. Artifacts without a valid receipt or an incomplete manifest also hold. Normal owner DML cannot update/delete/truncate receipts, artifacts, events or audit evidence. Deliberate owner DDL/data-store destruction remains outside that assurance.
- Private preflight pins the six reviewed function bodies/config/owner/language/arity/return types, exact private trigger namespace/definitions/enable modes, owner-only RLS policies, ACLs, rewrite-rule absence, expected object counts, and bounded literal catalog hashes for all eight private tables' columns/defaults/constraints/index definitions and both sequences' parameters/ownership. PostgreSQL18 native `contype='n'` entries are excluded because PostgreSQL17 represents NOT NULL in `attnotnull`; that column flag stays strictly pinned. No other constraint kind is ignored. It detects same-name public shadow functions, journal-swallowing rules and added default/CHECK/index expressions. **A future production coordinator must independently verify these descriptor contracts on the actual PostgreSQL version, inherited privileges and all live public registration/fence/v1 contracts.** This is a bounded reviewed private-DDL contract, not a general global-function dependency proof.

## Durable fence design

The proposed public guard is `BEFORE INSERT OR UPDATE OR DELETE OR TRUNCATE FOR EACH STATEMENT`, `ENABLE ALWAYS`. Every guarded statement locks the private singleton control row **FOR SHARE**, including while open. Activation updates that same row in a short transaction. This waits for existing guarded writers; committed active state survives the CLI or Render container dying. An old repeatable-read snapshot attempting the locking read after transition should serialize-fail rather than observe a stale open state. This last concurrency property is architecture-reviewed and requires the independent multi-session PostgreSQL tests below before live use.

TRUNCATE is always held. Active fences block ordinary direct owner writes as well as API and privileged RPC writes. The guard does not trust effective `current_user` inside SECURITY DEFINER, JWT claims, application name or a custom GUC. Bypass requires an explicit owner-only transaction permit bound to run, exact epoch, session-role OID, backend PID, transaction ID, allowed relation OIDs and operations. Permits last at most five minutes and cannot work in the next transaction; expiry fails closed. A fresh process/connection without a permit is blocked even if it uses the owner role.

Fence deadlines are short operational targets, **not automatic reopening**. After a deadline passes, writes remain blocked with a manual-recovery reason. Release requires the expected epoch, a fresh non-reused epoch and an audited explicit owner transition. A stale/NULL epoch cannot release a fence. This bounds intended maintenance duration while preserving safety if an operator/container disappears; prolonged outage requires independent owner database access and explicit abort/recovery, not a background expiry script. Existing CRM login paths that write fenced tables may fail, so verify the separate operator access path and application behavior before activation.

Closing capture must acquire the active control row's shared lock in its own transaction and bind its receipt to that exact epoch. Hold the lock through artifact/receipt commit so release cannot race the capture. Render Maintenance Mode alone is insufficient; it does not stop background/private writers. A newly LIVE deployment alone does not establish that the old instance and its in-flight work have ended.

## Remaining work before any production lifecycle

1. Obtain provisioned/used/free disk, current WAL/temp reserve and I/O headroom on both existing projects. Physical database/relation sizes are not upper bounds for raw JSON ciphertext. Measure bounded aggregate serialized bytes and actual maximum row sizes; account for both baselines, repeated closing snapshots, journal growth, WAL, temp files and long-snapshot tuple retention. No automatic resize or cost action is proposed.
2. Review/freeze the full per-site manifest. Current LIGHT metadata identified 335 primary / 339 backup base tables, 307 shared, 28 source-only, 32 target-only, 12 source-only no-PK snapshots, and 11 shared column drifts. Preserve source-only and target-only states; hold schema differences and unmatched historical tombstones/aliases. Do not infer that source absence means an authorized target delete.
3. Implement a separately reviewed lifecycle coordinator: actual-server verification of the exact private schema/default/constraint/index contracts; pinned public trigger/registration/function contracts; bounded-batch registration with durable receipts and schema drift handling; capacity attestations; closing-fence coverage across **all** approved tables; full v1/v2 journal enumeration; encrypted schema/state manifests; cross-site partial COMMIT/lost-ACK inspection and recovery. Nothing should acknowledge/prune by maximum event sequence, transaction ID or observation time.
4. Preserve v1's rejection of extra user/department triggers. Adding the v2 statement fence there changes the exact v1 catalog and three-row repair contract. A separately reviewed combined contract and permit minted **inside the actual repair transaction** are required before repair under that fence. Do not ignore extra triggers, replace the v1 body or rewrite old fingerprints. Any preparatory three-row snapshot becomes stale after approved catalog changes.
5. Run multi-session PostgreSQL tests for pre-fence writer drain, a transaction with an old repeatable-read/serializable snapshot, activation lock timeout/deadlock, simultaneous control transitions, permit cross-session reuse, release blocked by closing capture, and process/connection death before/after COMMIT. No local postgres/psql/docker test server is available; isolated PGlite's single connection does **not** prove these races. The new synthetic-only `vpt-cutover-postgres17.yml` workflow pins the official PostgreSQL17.6 OCI index digest and runs `replication-cutover-postgres17.js` against a fresh loopback-only disposable database. That harness uses distinct sessions and observed database lock barriers, kills only its own spawned child before/after COMMIT, and drops the successful COMMIT response through its own local TCP proxy to exercise actual lost acknowledgment. These proofs remain pending until the workflow passes at the reviewed final SHA; do not simulate them on production.
6. After complete durable both-site preservation and reviewed operational gates, deploy the guarded runtime with its old replication worker disabled, prove the old process stopped, take/verify a fresh combined-contract three-row snapshot, perform only that reviewed repair, and reconcile exact current identities/digests with held exceptions. Final closing needs real writer quiescence/drain and full committed-event re-enumeration. Historic lost RAM intent and storage-byte parity remain separately unresolved; current LIGHT mode has storage replication disabled.
